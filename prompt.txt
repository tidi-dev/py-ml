# PART S — DOCUMENTATION RULES

All tutorial material must follow these rules.

## Rule 1 — Plain language first

Bad:

> Minimize the empirical risk over the hypothesis space.

Good:

> The model adjusts itself so that its predictions are closer to the known answers in the training data.

Technical terminology may be introduced afterward.

---

## Rule 2 — Explain WHY

Do not write:

```python
model.fit(X_train, y_train)
```

and move on.

Explain:

```text
X_train
= information about the training examples

y_train
= correct answers for those examples

fit()
= ask the algorithm to learn relationships between them
```

---

## Rule 3 — Explain shapes visually

When useful, show:

```text
X

20,640 rows
×
8 features
```

versus:

```text
y

20,640 answers
```

Explain why there must be one target value for each observation.

---

## Rule 4 — Use concrete numbers

Prefer:

```text
Actual price    = $300,000
Prediction      = $270,000
Error           = $30,000
```

over purely abstract notation.

---

## Rule 5 — Avoid unnecessary jargon

When introducing a technical term:

1. explain the idea;
2. give an example;
3. give the official term.

For example:

> We want the model to work on houses it did not see during training. This ability is called **generalization**.

---

## Rule 6 — Include "Common Mistakes"

Each major tutorial should contain:

```text
Common beginner mistakes
```

Examples:

- evaluating on training data;
- confusing features and target;
- thinking `fit()` stores exact answers;
- assuming more features always improve the model;
- assuming a lower training error means a better model;
- comparing models using different test data;
- accidentally leaking target information.

---

## Rule 7 — Include checkpoints

End every tutorial with:

```text
Before continuing, I should be able to explain:
```

followed by approximately 3–6 questions.

Example:

```text
□ What is a feature?

□ What is the target?

□ Why can't MedHouseVal be included inside X?

□ Why do X and y have the same number of rows?
```

---

## Rule 8 — Include small exercises

Exercises should require me to think or write small pieces of code.

Do not immediately give the full answer.

Example:

> Exercise: Print the shape of `X`. Before running the code, predict how many rows and columns you expect.

Where appropriate, provide hints separately.

---

## Rule 9 — Connect topics together

Frequently remind me how concepts connect.

For example:

```text
Earlier:
We separated X and y.

Now:
We split both X and y into training and testing portions.

Next:
We'll use X_train and y_train to train our first model.
```

The material should feel like one course rather than disconnected articles.
